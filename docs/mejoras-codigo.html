Auditoría de seguridad y calidad — VitaLog

Alcance: implementación RU-02 (creación de hábitos), autenticación relacionada, configuración backend, repositorios MongoDB y cliente React. Fecha de análisis: 20 de noviembre de 2026.

Resumen ejecutivo: la implementación actual mantiene correctamente la creación de hábitos asociada al usuario autenticado y valida frecuencia, duración y nombre. No se encontró una vulnerabilidad crítica ni alta confirmada dentro del alcance revisado. Sí se identificaron dos puntos medios: la cookie de sesión no configura Secure y no existe limitación de intentos de autenticación. También se observaron oportunidades concretas de paginación, índice MongoDB y endurecimiento operativo.

1. Vulnerabilidades y riesgos de seguridad

MEDIA Sesión sin atributo de cookie Secure

Confianza: Alta.

Ubicación: backend/src/main/resources/application.properties.

Evidencia: se configura HttpOnly=true y SameSite=lax, pero no server.servlet.session.cookie.secure=true. Las demás configuraciones no establecen TLS ni proxy HTTPS.

Impacto: si la aplicación se publica por HTTP o un proxy permite conexión insegura, la cookie de sesión puede viajar sin cifrado y ser visible por terceros en la red. Esto podría permitir secuestro de sesión.

Recomendación: habilitar Secure en despliegues HTTPS y validar que el proxy configure correctamente el esquema de origen. Mantener el atributo HttpOnly y SameSite.

MEDIA No hay limitación de intentos de registro o inicio de sesión

Confianza: Alta sobre la ausencia observada; impacto operativo probable, no explotado.

Ubicación: SecurityConfig.java, AuthController.java y AuthService.java.

Evidencia: los endpoints públicos de login y registro no presentan filtros de velocidad, bloqueo temporal, reintentos ni mecanismos de protección conocidos en el código. El login usa BCrypt, que eleva el costo por intento.

Impacto: un atacante puede automatizar contraseñas o crear cuentas masivas, aumentando el consumo de CPU y la posibilidad de acceso no autorizado.

Recomendación: incorporar limitación por dirección/IP y por cuenta, con una ventana y bloqueo temporales. Aplicar además monitoreo de intentos fallidos y proteger explícitamente registro y recuperación futura.

BAJA MongoDB sin autenticación explícita en el contenedor local

Confianza: Alta en la configuración; riesgo condicionado al despliegue.

Ubicación: compose.yaml y application.properties.

Evidencia: el contenedor enlaza MongoDB únicamente a 127.0.0.1 y no define usuarios de MongoDB. La URI predeterminada usa mongodb://localhost:27017/vitalog.

Impacto: en el entorno actual el puerto no queda expuesto fuera del equipo. En otro entorno o si se modifica el compose, una instancia sin autenticación permitiría acceso directo a datos y cuentas.

Recomendación: conservar el enlace a loopback en desarrollo y configurar autenticación, secretos administrados y cifrado cuando exista una instancia compartida o productiva.

Controles positivos confirmados en RU-02

  • Autorización: POST /api/habits exige sesión autenticada y el servicio crea el hábito con el ID asociado al correo autenticado.
  • Validación: nombre obligatorio y máximo 100 caracteres, duración entre 1 y 3650 días, frecuencia requerida y días semanales limitados a valores válidos.
  • Protección CSRF: las operaciones POST usan token CSRF y la sesión cambia su ID al autenticarse.
  • Contraseñas: registro usa BCrypt y no se devuelve el hash en las respuestas.
  • XSS: React renderiza el nombre del hábito como texto mediante el DOM de React; no se encontró dangerouslySetInnerHTML ni manipulación directa de HTML.
  • Inyección NoSQL: no se encontraron filtros construidos con entrada de usuario ni consultas $where. Las consultas derivadas son tipadas por nombre de propiedad.

2. Malas prácticas y deuda técnica

OPORTUNIDAD CO-01 — Inconsistencia entre límite de caracteres y límite de bytes de contraseña

Confianza: Alta.

Ubicación: RegisterRequest.java, AuthService.java y AuthPage.js.

Evidencia: el DTO permite hasta 72 caracteres y el frontend define maxLength=72, mientras AuthService rechaza contraseñas que excedan 72 bytes UTF-8.

Impacto: una contraseña compuesta principalmente por caracteres multibyte puede ser aceptada por validación HTML/DTO y luego rechazada con un error posterior. Es una inconsistencia de experiencia de usuario y de validación.

Recomendación: definir una política única basada en bytes o, preferiblemente, limitar el resultado que el backend acepta y comunicar el mismo límite en texto y atributos del formulario. Evitar dos reglas similares que puedan divergir.

OPORTUNIDAD CO-02 — Dependencia obsoleta del frontend

Confianza: Alta.

Ubicación: frontend/package.json y README.

Evidencia: el proyecto usa Create React App/react-scripts 5.0.1 y React 18.3.1. El propio README reconoce que CRA está obsoleto.

Impacto: menor soporte para nuevas herramientas y posibles dificultades al incorporar parches o mejoras de seguridad de la cadena de construcción.

Recomendación: planificar una migración por etapas a una herramienta mantenida, ejecutando primero las pruebas y verificando el empaquetado estático.

OPORTUNIDAD CO-03 — Estado de carga puede quedar desalineado tras un error de creación

Confianza: Media.

Ubicación: frontend/src/pages/WelcomePage.js, variable createdDuringLoad.

Evidencia: se marca createdDuringLoad.current = true antes de enviar la creación y nunca se restablece en el bloque de error o éxito. Esta bandera evita que una respuesta de carga inicial sobrescriba el hábito recién creado.

Impacto: si la creación falla mientras una carga inicial sigue en curso, la carga posterior puede quedar descartada y la lista no actualizarse durante la vida del componente.

Recomendación: reemplazar la bandera por una cancelación de carga o por una sincronización basada en identificadores de solicitud y estado de montaje. Gestionar por separado éxito, error y carga de la lista.

3. Rendimiento y arquitectura

OPORTUNIDAD RE-01 — Consulta de hábitos sin índice específico ni paginación

Confianza: Alta sobre la implementación actual; impacto depende del volumen.

Ubicación: HabitController.java, HabitRepository.java y Habit.java.

Evidencia: findByUserIdOrderByStartDateDesc devuelve toda la colección filtrada por usuario sin Pageable. El campo userId no tiene índice y el campo startDate no forma parte de un índice compuesto.

Impacto: al crecer el número de hábitos o usuarios, MongoDB puede recorrer más documentos y ordenar resultados en memoria. La interfaz recibirá una lista completa aunque solo muestre una cantidad limitada.

Recomendación: crear un índice compuesto en { userId: 1, startDate: -1 } y aceptar Pageable o cursores con límite en la consulta y el API. Mantener el orden descendente previsto por RU-02 y evolucionar la interfaz hacia carga paginada.

OPORTUNIDAD RE-02 — Mejorar aislamiento de lógica y reutilización de carga

Confianza: Media.

Ubicación: HabitController.java, HabitService.java y WelcomePage.js.

Evidencia: el listado resuelve la cuenta y consulta el repositorio directamente desde el controlador, mientras la creación delega en el servicio. El frontend combina estado de formulario y estado de hábitos en un único componente grande.

Impacto: aumenta el costo de pruebas y hace más probable duplicar lógica de usuario o mantener estados concurrentes. No representa una vulnerabilidad confirmada.

Recomendación: trasladar el listado completo al servicio y separar componentes de formulario y listado. Mantener inyección por constructor, que ya facilita las pruebas unitarias.

4. Alcance del código revisado

Se revisaron requisitos RU-02, configuración de seguridad, controladores y servicios de autenticación/hábitos, DTO, modelo y repositorios MongoDB, cliente React y pruebas de integración disponibles. También se revisó el archivo Compose y la documentación técnica inicial.

Limitaciones y verificaciones adicionales

  • No se realizaron ataques ni pruebas contra sistemas externos.
  • No se verificó un despliegue HTTPS real, encabezados de infraestructura, configuración de reverse proxy ni protección distribuida frente a fuerza bruta.
  • No se analizaron dependencias binarias más allá del manifiesto Maven/package-lock disponible.
  • No se encontró evidencia suficiente para afirmar vulnerabilidades de CORS, JWT, XSS o inyección NoSQL; no existen JWT en el flujo revisado y se usa sesión/cookie CSRF.
  • Verificar con un escaneo de dependencias actualizado y pruebas de carga antes de producción.
  • La funcionalidad del resto de RU-03 a RU-11 no está implementada en el código revisado y queda fuera de una conclusión sobre esas prestaciones.
